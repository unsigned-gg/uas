## Findings the builders must know

1. **No worker is ever enrolled in a slot cgroup [verified]:** `grep -rn 'add_pid\|cgroup.procs' crates --include=*.rs` hits only `freezer.rs` (the trait at line 114, the impls at 538 and 667) and tests. `launch::spawn_worker` (`launch.rs` line 143) runs `cmd.spawn()` with the `enter_clamped_group` hook and never writes the pid to `cgroup.procs`. So today `cpu.max`, and every limit this spec adds, constrain no process. The spec assumes enrolment ("written before the first `exec` in the slot", REQ-0041-01 and 08). P6 adds it. It is not a Plan item of the spec (OPEN for the integrator to confirm).
2. **There is no `allocate`, and no `Reclaiming` code [verified]:** `grep -n 'pub fn allocate' crates/uas-pool/src/slot.rs` prints nothing, and `grep -rn Reclaiming crates/uas-pool/src crates/uas-domain/src` prints nothing. The slot cgroup is made by `SlotPool::create_slot` (`slot.rs` line 157, through `CgroupFreezer::new`). The worker is reaped and its receipt sealed in `Worker::finish` (`launch.rs` line 96). So: `MemoryLow` and `DiskLow` are checked in `create_slot` before `CgroupFreezer::new`; the events are read in `Worker::finish`. When spec 0036 adds `SlotPool::allocate`, the two checks move to its top, before it takes a host slot lock, so a refused allocation holds no host slot.
3. **`host_max_slots` does not exist yet; read `PoolConfig::max_slots` [verified]:** `grep -rn host_max_slots crates --include=*.rs` prints nothing. `max_slots` (`slot.rs` line 23, default 2) is the in-process cap of spec 0015 D1. P5 adds `PoolConfig::host_max_slots(&self) -> usize` returning `self.max_slots`, so the one call site changes when spec 0036 adds the field. Every package below can land before spec 0036's arbiter. Overlap is textual only: both specs edit `PoolConfig`, `PoolError` and `slot.rs`, so the second to land rebases (the same note as plan 0040, finding 1). The benches build `max_slots: 10`, which gives `MemTotal / 20`; that is above the floor on any host with 40 GiB or more, and the check runs only when `cgroup_base` is set (finding 6).
4. **The receipt the spec names is not one type [verified]:** `AuditReceipt` is the wire frame in `crates/uas-ebpf/src/audit.rs` (line 87: `run_hash`, `events`, `dropped_events`, `attested`, `cpu_cap`). The daemon has no cgroup data, so `oom_kill` and `pids_max_hits` cannot be made there. The pool-side record is `WorkerAudit` (`launch.rs` line 55), "the landing reads them as its input", and `LandingFacts` (`crates/uas-domain/src/landing.rs` line 48 holds `cpu_cap`) is the stored receipt. P1 and P6 put the counters on `WorkerAudit`. Carrying them on to `LandingFacts` and `LandingInput` (`crates/uas-engine/src/landing.rs` lines 56 and 300) is a further change that the spec's Plan does not list and no Test row needs (OPEN, see the end).
5. **Counters are cumulative per cgroup [asserted from cgroup v2 semantics]:** `memory.events` `oom_kill` and `pids.events` `max` count since the cgroup was made, and a slot serves many workers. P6 reads a baseline at spawn and records the delta at `finish`, the way `Tracking.baseline` does for dropped events (`launch.rs` lines 68 to 72).
6. **Limits only make sense with a cgroup [asserted]:** with `cgroup_base: None` the pool uses `SignalFreezer` and no limit file exists. P5 runs the `MemoryLow` check only when `cgroup_base` is `Some`, so no existing test on a small host starts to refuse. The `DiskLow` check runs only when the new `disk_root` field is `Some`. Both defaults are `None`.
7. **`SlotPool::new` is infallible and built by seven all-field literals [verified: `grep -rn 'PoolConfig {' crates`]:** `tests/lifecycle.rs` lines 36 and 170, `tests/launch.rs` line 297, `tests/reconcile.rs` lines 100 and 212, `benches/slot_lifecycle.rs` lines 80 and 110 build `PoolConfig` with every field and no `..Default::default()`. P5 edits those seven literals. `new` stays infallible: P5 stores the resolved limits, or the refusal data, and `create_slot` returns `MemoryLow` from it (REQ-0041-11 says `allocate` refuses, not the constructor). `PoolError` is not `Clone`, so the stored refusal is plain data and the error is built per call.
8. **`ResourceLimits` has two all-field literals in tests and one in the bench [verified]:** `tests/freezer.rs` lines 115 and 160 and `benches/slot_lifecycle.rs` line 145. P3 adds two fields (`pids_max`, `memory_swap_max_bytes`) and edits those three literals. The struct stays `Copy`.
9. **`configure_limits` skips a missing memory file silently [verified]:** `freezer.rs` lines 387 to 408 test `memory.high` and `memory.max` with `exists()` and write nothing, with no log. D4 and REQ-0041-05 require a `warn`. P3 fixes it for all four files.
10. **`CgroupFreezer::new` ignores the result of `configure_limits(&ResourceLimits::default())` [verified: `freezer.rs` line 289].** `Default` has no host knowledge, so memory cannot come from it. P3 adds `CgroupFreezer::with_limits(base, id, &ResourceLimits)` and keeps `new` as `with_limits(.., &default())`; P5 calls `with_limits` with the resolved values. The write is then in the same call as the directory creation and before any worker exists (D4).
11. **`/sys/fs/cgroup/uas` is not needed for a no-sudo live proof, but the process cgroup alone is not enough [verified 2026-10-11 as uid 1000 on ceres]:** a child of the herdr service cgroup has `cpu.*` and `memory.pressure` but no `memory.max`, `memory.swap.max`, `memory.events`, `pids.max` or `pids.events` (`cgroup.subtree_control` of the parent is empty, and enabling it there is refused while the cgroup holds processes). This works: `systemd-run --user --scope -q -p Delegate=yes bash -c '...'`, then inside it make `$C/leaf`, write `$$` to `$C/leaf/cgroup.procs`, write `+memory +pids` to `$C/cgroup.subtree_control`, and `mkdir $C/slot-x`. The listing then shows `memory.events memory.max memory.swap.max pids.max`. P7's live test does that setup itself and skips with a printed line when it fails; the builder runs it inside the scope. Plan 0040 finding 8 (a child of the process cgroup) does not carry over to memory and pids. Not yet exercised by me: an actual OOM kill in such a cgroup.
12. **The spec's "run under `make ebpf-test`" cannot hold [verified]:** the recipe (`Makefile` lines 87 to 90) runs only the `uas-ebpf` binary `live_probes`, and `uas-ebpf` sits below `uas-pool` in the layering, so a pool test cannot live in that binary. CI (`.github/workflows/ci.yml` lines 180 to 197) fails on any `skipped:` line but one and requires `9 passed`. Same conflict as plan 0040 finding 7. P8 holds the make hook (BLOCKED). P7's proof does not need it.
13. **The 4 GiB allocation does touch memory [verified]:** `python3 -c "x=bytearray(2**32)"` reports `ru_maxrss` 4106 MiB right after the allocation, so the spec's OOM command charges the cgroup and can go red. A `pids.max` 64 fork loop is in the spec Test table; it must keep children alive until the limit is hit (a loop that reaps each child never reaches it).
14. **Spec 0038 and PR #119 [verified]:** PR #119 (`docs(spec-0038): amend WorkerSlot CRD to carry spec.limits`) is MERGED, but into `main` (`gh pr view 119 --json baseRefName` prints `main`). `git show origin/main:specs/0038-uas-operator-and-crds.md` has D10 and REQ-0038-13; `origin/development` has neither (`grep -n limits` hits only line 60). They reach `development` with the next promotion or a back-merge. The spec 0041 Plan item "add `spec.limits` to spec 0038" is therefore done and needs no package. Defect for the owner of 0038, not fixed here: its D10 still names `CAS_SLOT_MEMORY_MAX` where spec 0041 D7 says `UAS_SLOT_MEMORY_MAX`. The operator side is not built: `ls crates` has no `uas-operator`. P9 is BLOCKED on that.
15. **No new dependency [verified]:** `rustix` (pinned in spec 0004 line 177, features `std`, `process`, `thread`, `fs`, `mount`) has `fs::statvfs` under its `fs` feature, and `uas-pool` already depends on it (`Cargo.toml`). `/proc/meminfo` is read with `std::fs`. The cgroup enrolment write uses `rustix::io::write` on a pre-opened descriptor inside the existing `pre_exec` `unsafe` block pattern (`launch.rs` line 153). `PINS: none`.
16. **Rounding is not in the spec (asserted):** `memory.high` is `max * 4 / 5` in integer bytes, floor. The spec's "10.8 GiB" and "51.2 GiB" are the exact products, so the fixture asserts `13.5 GiB * 4 / 5` in bytes (11596411699) and `64 GiB * 4 / 5` (54975581388), not a decimal GiB figure. `MemTotal` in `/proc/meminfo` is in kB; the formula is `kB * 1024 / (2 * host_max_slots)`, and the fixtures are 6, 54 and 256 GiB written as kB.
