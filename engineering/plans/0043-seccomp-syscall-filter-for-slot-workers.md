The workspace MSRV is 1.89 (`Cargo.toml` line 10); a clean `cargo build` and `make toolchain-check` under the pinned toolchain is the only proof, so P2 runs them [MSRV unverified].
2. **Row shape for spec 0004 [verified: `xtask/src/pin_check.rs` lines 126-188]:** `parse_pins` reads only tables whose header cells are exactly `Crate` and `Version`. The table at `specs/0004-dependency-and-licence-policy.md` line 173 qualifies: `| Crate | Version | Licence | Used by | Phase | Conditions |`. Cell 0 is the crate name in backticks, cell 1 must be a bare `X.Y.Z` (no `=`, no `^`). The first table (line 135 header `| Project | Licence ...`) is NOT parsed, so a row there is documentation only; D7 says "both tables", so P1 writes both. A crate with no row is skipped, so `make pin-check` stays green with no row; once a manifest declares a crate that has a row, the lockfile must hold exactly that version. The new row must read `` `seccompiler` | 0.5.0 `` with the lockfile at 0.5.0, or `make pin-check` fails.
3. **`libc` is a hidden second pin, and BLOCKED [verified]:** `seccompiler` keys its rules by raw syscall number (`SeccompFilter::new(rules: BTreeMap<i64, Vec<SeccompRule>>, ...)`, `backend/filter.rs` line 85), and its own docs get the numbers from `libc::SYS_*`. `rustix` 1.1.5 (the approved syscall crate) exports no syscall numbers. So `seccomp.rs` needs `libc` as a direct dependency of `uas-sandbox` (or hand-typed per-architecture number tables, which I advise against). Spec 0004 line 180 pins `libc` at 0.2.169 and says "NOT in the workspace" by a lane ruling of 2026-10-09; `Cargo.lock` holds 0.2.190 (`grep -n 'name = "libc"' -A1 Cargo.lock`, line 2221). The day a manifest declares `libc`, `pin-check` fails with `libc pinned 0.2.169 ... Cargo.lock has 0.2.190`. The integrator must rule (R1 below). The test rows of P4 also need raw `syscall(2)` for `ptrace`, `keyctl`, `bpf`, `perf_event_open`, `open_by_handle_at` and `clone`, which `rustix` features enabled today cannot issue, so the same ruling covers a `libc` dev-dependency.
4. **A `SeccompFilter` has one `match_action` [verified: `backend/filter.rs` line 85-89].** D2 needs `EPERM` for the list and `ENOSYS` for `clone3`. The builder installs TWO programs, one per verdict, in the same `pre_exec` step. The sets are disjoint (`clone3` is only in the second), so the kernel's most-restrictive-wins rule never has to break a tie [asserted from seccomp(2); the escape rows prove it]. `Seccomp_filters` in `/proc/self/status` therefore grows by 2, not 1. D5 says "install without TSYNC": `seccompiler::apply_filter` (not `apply_filter_all_threads`) [verified: `lib.rs` lines 312-326].
5. **`apply_filter` is safe in `pre_exec` [verified: `lib.rs` lines 336-368]:** it calls `prctl(PR_SET_NO_NEW_PRIVS)` and `seccomp(2)` and allocates nothing on the success path. Building the program allocates, so P2 builds the `BpfProgram` in the parent, before fork, and the `pre_exec` closure only calls `apply_filter` on the borrowed program. Build failure then surfaces at `launch` time in the parent (D4: `JailRefused`); an install failure in the child reports `JAIL_REFUSED_ERRNO`.
6. **Hook order [verified: `crates/uas-sandbox/src/launcher.rs` lines 28-40, 49-51 and `tests/escapes.rs` lines 358-361]:** `netns::isolate(&mut command)` is called by the caller before `launch`; `launch` calls `jail`, which registers one `pre_exec` (`restrict_child`). `std` runs `pre_exec` closures in registration order, so the seccomp hook must be registered after `restrict_child`'s. `jail` is `pub` and re-exported (`lib.rs` line 24); other callers are only `launch` and the tests [verified: `grep -rn "jail(\|launch(" crates`]. Keep `jail` Landlock-only and add the filter in `launch`: that matches D1, and it gives P4 the unfiltered baseline D8 needs.
7. **Over-denial risk for P4 [asserted, check on a real run]:** the existing rows `ping_raw` (`socktype: SOCK_RAW`) and `setuid_sudo` run inside the filter now. `ping`'s raw socket fails with `EPERM` either way, so `raw-socket-denied` should still match; the builder confirms it and reports any drift to the integrator instead of editing a spec 0012 expectation. `glibc` falls back from `clone3` to `clone` on `ENOSYS` (D2 says so), so thread and process spawn in the helper keep working; REQ-0043-09 is the proof.
8. **Several D6 rows cannot go red by removing the filter [asserted by kernel behaviour, to be measured by the builder]:** an unprivileged process already gets `EPERM` from the kernel for `bpf`, `open_by_handle_at`, `mount` (no `CAP_SYS_ADMIN`) and `socket(AF_PACKET)` or `SOCK_RAW` (no `CAP_NET_RAW`), and often for `perf_event_open` (paranoid sysctl). Only `ptrace_self`, `keyctl_session`, `unshare_user`, `clone_newuser`, `clone3_enosys` and probably `io_uring` succeed unfiltered. The spec's Test table claims red-first only for `ptrace_self`, `unshare_user`, `clone_newuser`, `clone3_enosys` [verified: spec Test table]. P4's red-first control is to comment out the install call once, run the matrix, and record in the verdict which rows stayed green. A row that stays green is kept (the spec requires it) and labelled "kernel also denies" in its comment. See OPEN 3.
9. **Argument rules the builder needs, as implementation of D2, not changes to it [asserted from the seccompiler API: `SeccompCondition::new(arg_index, SeccompCmpArgLen, SeccompCmpOp::MaskedEq(mask), value)`, rules in a `Vec` combine with OR, conditions inside one rule combine with AND, an empty `Vec` matches unconditionally]:** `clone` is denied when `arg0 & CLONE_NEWUSER == CLONE_NEWUSER` (64-bit compare). `socket` is denied by two ORed rules: `arg0 == AF_PACKET` (32-bit), and `arg1 & 0xf == SOCK_RAW` (`SOCK_CLOEXEC` and `SOCK_NONBLOCK` are OR-ed into the type, so an unmasked equality compare would miss `SOCK_RAW | SOCK_CLOEXEC`).
10. **x32 on x86_64 [asserted, not in the spec]:** `seccompiler`'s architecture check kills on a wrong `AUDIT_ARCH` value (`backend/bpf.rs` lines 73-78), but an x86_64 process can still use the x32 syscall numbers (bit 30 set) under the same `AUDIT_ARCH_X86_64`, which would miss every deny entry. This is the same class as D3. Whether it is reachable depends on `CONFIG_X86_X32_ABI` of the host kernel. Not a package; see OPEN 4.
11. **Spec 0012 would depend on spec 0043 while spec 0043 depends on 0012 [verified: `depends_on` lines of both]:** `xtask/src/spec_check.rs` checks only that each `depends_on` entry is a spec (line 507) and has no cycle test (`grep -in 'cycle\|circular'` prints nothing), so P5 passes `make spec-check`. The mutual edge is the spec's own Plan item; see OPEN 4.
12. **Spec 0043's D2 carries no "proposed" marker [verified: `grep -n -i 'proposed\|pending' specs/0043-*.md` finds one unrelated line].** The brief says D2 is proposed pending the research lane's pass; the spec text records that the research lane's critic pass already added `kcmp`, `setgroups`, `umount` (D2 source column). Either way every builder prompt below says: do not add, remove or reorder a D2 entry, and do not change the `clone3` verdict.
